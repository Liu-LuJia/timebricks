## 更新行为

1. 启动后延迟 8 秒异步检查；每 24 小时最多自动尝试一次，包括失败。只在设置入口显示「新版本」，不弹窗、不下载、不通知。手动检查不受此限制。检查时间和发现的新版本持久保存，重启当天仍可显示提示；下次成功检查会更新缓存。
2. 正式版标签使用 `v1.2.3` 或 `1.2.3` 等数值格式，以数值比较，避免把 `1.10` 误判为低于 `1.9`；不猜测无法识别的版本标签。最新正式版没有 APK 时会说明，不偷偷退回旧版。
3. 查看更新说明后选择 APK，确认下载大小和流量。多个 APK 由用户选择，下载后核对设备架构。全程显示已下载/总大小及校验状态，可取消，失败可重试。
4. 仅从配置仓库的 HTTPS Release 附件地址下载。使用私有缓存目录，校验实际长度和 GitHub 返回的 SHA-256 digest；缺失或不匹配均停止。限制单包不超过 512 MB，处理存储空间不足。
5. 下载后检查 APK 可读性、包名、递增的 versionCode、与 Release 标签一致的 versionName、最低系统版本、签名证书集合及原生库 ABI。不同签名（包括 debug 与正式签名、证书轮换）保守拒绝，不尝试卸载。系统安装器仍会最终验证 APK 密码学签名及设备策略。
6. 校验通过后用户点击「安装更新」。如未允许安装未知应用，用应用统一样式说明，再打开系统授权页。返回后再次点击安装；拒绝授权或取消安装会保留本次文件供重试，不报告虚假的安装成功。
7. FileProvider 只共享 `cache/app-updates/`，不暴露日程文件。取消/失败会清理本次文件；网络读取超时最多 15 秒，取消后可能等待阻塞读取结束才清理。旋转屏幕、页面切换不会丢失下载状态；进程被系统终止后需重新下载，不提供断点续传。重启清理超过 24 小时的旧下载缓存。

## 自行真机验证

1. 先导出备份。在 Android Studio 打开项目并使用现有签名方式安装，保留当前数据。核对规划、日程、统计、提醒、模板、备份仍可操作。
2. 打开设置最底部「关于时间积木」，检查图标、名称、实际版本、作者、未配置邮箱和群号；复制群号到 QQ，查看功能详情和各级返回。
3. 切换浅色、深色、主题色、字号、圆角并重启；检查纯黑页面背景、分组及弹窗颜色、左侧导航。再把系统字体增大，检查小屏/横屏下文字可读、按钮可点、内容可滚动。
4. 无 Release 时检查空状态；断网后手动检查应显示失败且可重试。日程页面不应被弹窗打断。真实 Release 发布后检查记录日期倒序、摘要和详情一致。
5. 准备同包名、同签名、更高 versionCode 且标签匹配的测试正式版，确认新版本提示、下载前确认、进度、取消、重试和校验通过。启动后等待 8 秒，观察只出现入口提示；当天重启不再次自动请求，不自动下载。
6. 在下载中切换页面或旋转屏幕，确认返回可见进度。分别测试断网、取消以及系统终止进程；后者应可重新下载，不把残缺文件当作有效 APK。
7. 使用专门测试仓库/测试构建验证错误包名、相同/更低 versionCode、签名不同、版本名不符、校验值不符/缺失及过高 minSdk 均被拦截；不要为测试替换正式 Release 的正常附件。
8. 首次安装选择不授权，确认可返回；再授权并点击安装。测试系统安装取消后可重试，最后完成覆盖安装并核对日程、主题和备份配置仍在。检查新版版本号改变且不再提示旧更新。

安装与后台行为尚需用户荣耀真机验证；编译和单元测试通过不等于安装闭环或所有设备兼容性通过。
